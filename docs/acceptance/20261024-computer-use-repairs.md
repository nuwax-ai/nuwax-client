## 开关被关闭：已复现的原因与修复

代码层面已复现两条状态丢失路径，失败回归先提交于 `19144149`，当时两项均失败：

1. `step1_config` 同时承载普通设置和 CU 字段，普通设置保存采用整个对象替换。旧快照中缺失/过期的 `computerUseEnabled` 能覆盖用户刚才的选择；写回旧的 true 同样能复活本已关闭的开关。
2. `setCuaEnabled(true)` 在恢复过程中先写 false；安装、授权或就绪失败后又通过 disable 清理持久化 false。已有 ON 用户在失败恢复后会失去原偏好。

修复：CU 字段迁入特性独立的 `computerUsePreferences.v1`，初次从本产品现有 step1 字段迁移。该记录是唯一事实源；step1 仅作旧客户端兼容投影。通用设置的保存、清空或旧快照不能再覆盖该记录。首次安装缺省 OFF；明确开启成功才 ON，明确关闭仍 OFF。恢复失败撤销 MCP、停止执行，保留原 ON 偏好；数据库写入失败也必须完成执行资源的撤销。

新增回归覆盖旧快照覆盖/复活、已有 ON 恢复失败、明确 OFF、数据库写入失败后的停止，以及既有启动/撤权状态保留。持久化日志只记录 enabled 布尔值和原因，不记录设置内容。

**原来那一次真机反馈仍不能认定唯一触发源。** 当时缺少完整的升级前后配置写入时间线。本轮消除了已复现的两条代码路径；原事件最终关闭仍需下面的 ON→ON 实包升级证据，不能把源码测试当成已经重现原设备事件。
