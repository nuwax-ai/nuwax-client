# 实施计划：glibc 2.28 容器内构建 Linux 原生件

- 状态：已完成（2026-11-25，v3.3.0-beta.5 起生效；UOS 1050 arm64 真机验收通过，未覆盖的部分见「偏离记录」末尾）
- 目标：UOS 20 Pro 1050（glibc 2.28，arm64 与 x64）上，Nuwax 客户端安装后原生件能加载。

## 一、问题与结论

CI 在 `ubuntu-24.04`（glibc 2.39）上编原生件，产物带 `GLIBC_2.34`～`GLIBC_2.39` 的符号，UOS 1050 只有 2.28，加载即失败。
安装不受影响（dpkg 只拷文件），Electron 自身也不受影响（只需 2.25），失败的只有我们自己编的原生件。

**结论：把 Linux 原生件的编译放进 Debian 10 buster 容器（glibc 2.28），打包流程留在 runner 上不动。**

### 已经实测验证的部分（2026-11-24）

| 原生件 | 在 buster 里的构建方式 | 最高 GLIBC（CI 现状） | UOS 真机 |
|---|---|---|---|
| `better_sqlite3.node` | gcc 8.3 + `g++` 垫片，与 `rebuild:better-sqlite3` 相同参数 | 2.28（2.34） | 在真实 Electron 43.8.12 里加载成功；CI 版加载失败 |
| capture `ffmpeg` 8.1.3 | gcc 8.3 + nasm；探针脚本照仓库的 configure 参数手抄，**未跑仓库的 `prepare-release-capture.mjs`** | 2.28（2.38） | H.264 / VP9 编码解码、滤镜通过；CI 版 `GLIBC_2.38 not found` |
| `NuwaxComputerUse` | **仓库的 `build-helper.sh`，一行未改** | 2.28（2.39） | `cua-driver 0.38.0` 正常启动；CI 版缺 3 个符号起不来 |

- arm64 三项都做了完整构建并在 UOS 真机验证；x64 只验证了 `better_sqlite3.node` 的构建，未在真机验证（没有 x64 的 UOS 机器）。
- `better_sqlite3.node` 和 `NuwaxComputerUse` 是用仓库自己的脚本/参数编的；**capture ffmpeg 还没用仓库脚本跑过**，是实施第 1 步要先补的验证。
- 产物从容器搬到 glibc 更新的系统（strip + 重新打包）后，最高 GLIBC 仍是 2.28 —— 这是「容器只管编译」成立的前提。

### 不在容器能力范围内的

`agent-desktop` 的两个 Linux 二进制是**上游 npm 预编译**（`agent-desktop@1.2.0`），arm64 版需要 GLIBC 2.34，容器解决不了。见第五节。

## 二、为什么是「只把编译放进容器」，而不是整个 job 进容器

`build-electron` 是一个 649 行的 job，Linux 要走其中约 35 步（checkout、子模块、pnpm、资源下载、electron-builder 出包、上传）。整个 job 进 buster 会引入一堆与目标无关的风险，已确认的一处：

- **arm64 打包依赖系统 fpm**（electron-builder 内置的 fpm 只有 x86 版），workflow 用 runner 上的 `ruby` + `gem install fpm`。buster 的 ruby 是 2.5，新版 fpm 未必支持。

只把 3 个编译步骤放进容器，其余全部不动，改动面从「35 步」缩到「3 步 + 1 个门禁」。

## 三、镜像

### 3.1 内容

以 `debian:10` 为基础（官方多架构，`linux/amd64` 与 `linux/arm64` 都有），预装：

| 组件 | 版本 | 用途 | 为什么必须自己装 |
|---|---|---|---|
| gcc / g++ / make / ld | buster 自带 8.3 | 编译 | — |
| `g++` 垫片 | 仓库脚本生成 | 把 `-std=c++20` 改写为 `-std=c++2a` | gcc 8.3 不认识 `-std=c++20` |
| Python | 3.12.16（python-build-standalone） | node-gyp 13 | buster 自带 3.7，gyp 用了海象运算符 |
| Node | 24.14.0（官方二进制） | node-gyp、构建脚本里的 node 调用 | 裸镜像没有 |
| git | 2.47.1（源码编译） | `build-helper.sh` 的 clone | **buster 自带 2.20.1 不支持 `--filter=blob:none` 和 `sparse-checkout`**，脚本会以 128 退出 |
| rustup + Rust | 1.97.1 + rustfmt | cua-driver | 与 `.github/actions/native-build-cache` 锁定的版本一致 |
| X11 / dbus / xkbcommon 开发库 | buster 自带 | cua-driver 链接 | 与 workflow 现在装的同一组 |
| nasm、pkg-config、clang | buster 自带 | capture ffmpeg | 与 workflow 现在装的同一组 |
| **curl** | **7.74（buster-backports）** | 仓库的下载脚本 | **buster 自带 7.64 不支持 `--retry-all-errors`**（7.71 起才有），仓库有 3 处用了它。backports 源只在安装 curl 时启用，装完即移除 |
| `file`、`binutils`（readelf） | buster 自带 | 排查问题用；门禁自己解析 ELF，不依赖它 | — |
| sudo、ca-certificates、xz-utils | buster 自带 | 通用 | GitHub 的 action 需要 |

**版本全部写死在 `versions.env` 里**，包括每个下载的 URL 和 SHA256。Node 和 rustup 的哈希对照过官方校验文件；python-build-standalone 和 git 没有官方校验文件，是自行计算的。

### 3.2 文件位置

```
docker/linux-native/Dockerfile        # 多架构，一份
docker/linux-native/gxx-shim.sh       # 生成 g++ 垫片
docker/linux-native/versions.env      # 所有版本号与校验和，单一事实源
.github/workflows/linux-native-image.yml   # 构建并推送镜像
```

### 3.3 托管

推到 **GHCR**：`ghcr.io/nuwax-ai/nuwax-linux-native:<tag>`。仓库是 public 的，镜像也设为 public，CI 拉取不需要凭据。

tag 规则：`<日期>-<Dockerfile 内容哈希前 12 位>`，例如 `20261201-a1b2c3d4e5f6`。镜像内容一变 tag 就变，workflow 里引用的 tag 也必须跟着改 —— 用的是哪个镜像一眼可查，不会被「latest」悄悄换掉。

### 3.4 构建方式

单独一个 workflow `linux-native-image.yml`，`workflow_dispatch` 手动触发（或 `docker/linux-native/` 下文件有改动时自动触发）：

1. `docker/setup-buildx-action` + `docker/build-push-action`，`platforms: linux/amd64,linux/arm64`，用 QEMU 跑另一个架构的构建；
2. 推到 GHCR，权限 `packages: write`；
3. 构建后立刻在镜像里跑一遍三个编译，任何一个 GLIBC 超过 2.28 就失败 —— 镜像本身不合格就不发布。

镜像是低频变更（只在升级工具链时重建），不需要每次 CI 都构建。

## 四、接入 CI

### 4.1 调用方式

在 workflow 里用 `docker run` 调镜像，而不是 `jobs.<id>.container:`（后者会把整个 job 放进容器，正是第二节要避免的）。写一个复合 action 统一入口：

```
.github/actions/linux-native-run/action.yml
```

用法：`uses: ./.github/actions/linux-native-run` + `with: command: <要跑的命令>`。它做的事：

1. 把 workspace 挂进容器（同一路径，避免绝对路径错位）；
2. 挂上 pnpm store、cargo registry、`~/.cache/node-gyp` 等缓存目录；
3. 以 runner 的 uid/gid 运行（避免产物变成 root 所有，后续步骤写不了）；
4. 传入 `TARGET_ARCH`、`RUNNER_TEMP` 等必要环境变量；
5. 镜像 tag 从 `docker/linux-native/versions.env` 读，workflow 里不手写。

### 4.2 三个步骤的改法

| 步骤 | 现在 | 改后 |
|---|---|---|
| Rebuild native modules for Electron | `npm run rebuild:better-sqlite3` | 在容器里跑同一条命令。产物落在 `node_modules/better-sqlite3/build/Release/`，位置不变，后续步骤无感 |
| Prepare and admit capture release resources | runner 上跑 `prepare-release-capture.mjs` | 在容器里跑同一条命令。走的是现成的缓存产物机制 |
| Build Computer Use helper (cua-driver) | runner 上跑 `build-helper.sh` | 在容器里跑同一条命令。同上 |

「Install Linux build tools」「Setup Linux capture compiler」两步对 Linux 保留（runner 上的 fpm/rpm 还要用），但可以去掉与容器重复的部分。

非 Linux 平台的这三个步骤完全不动。

### 4.3 对缓存的影响

- `HELPER_RECIPE` / `CAPTURE_RECIPE` 本身不变（它们只列源码和脚本）。
- 但缓存键里的 `nativeTools()` 会变 —— 它探测 gcc、ld、pkg-config 和各库版本，容器里是 gcc 8.3 而不是 runner 上的 gcc 13。**所以换容器后 helper 和 capture 的缓存会失效一次**，冷编一轮（arm64 上 cua-driver 约 95 秒，ffmpeg 几分钟），之后恢复命中。
- 按 AGENTS.md 的缓存配方纪律：这是有意为之的一次性冷编，**不需要** bump `RESOURCE_STAGING_CONTRACT` —— 暂存文件集和 manifest 准入契约都没变。
- `better-sqlite3` 不走这个缓存，每次都编，约 10 秒。

### 4.4 门禁：扫描包内每个 ELF

新增 `scripts/client/linux-glibc-gate.mjs`，接在现有的 `package-payload.mjs --verify-output` 之后（那一步 CI 已经在跑）：

- 遍历 `linux-<arch>-unpacked/` 下所有 ELF 文件，读 `.gnu.version_r` 段，取最高的 `GLIBC_x.y`；
- 任一文件超过 `2.28` 即失败，报出文件名和所需版本；
- **带白名单**，并要求白名单每项写明原因和到期条件，否则以后有人为了过门禁随手加：

| 文件 | 原因 | 处理 |
|---|---|---|
| `resources/agent-desktop/linux-*/agent-desktop-*` | 上游预编译 | 见第五节 |

现有实现可复用：`linux-package-policy.cjs` 里已有 `highestGlibcVersion` / `checkGlibcFloor`，门禁是把它从「单文件检查」扩成「目录遍历 + 白名单」。

这门禁的价值在于**防回归**：以后谁在容器外编了东西、或换了依赖带了新的原生件，CI 会直接拦下，而不是等 UOS 上装了才发现。

## 五、agent-desktop：需要你决定

`agent-desktop` 是 Computer Use 的一个可选引擎（默认是 CUA Driver）。它的 Linux 二进制来自上游 npm 包 `agent-desktop@1.2.0`，我们这边只对 Windows 版自编（`buildWindowsDesktop`）。arm64 那两个需要 GLIBC 2.34。

| 选项 | 做法 | 代价 |
|---|---|---|
| A | 找上游出一个按旧 glibc 编的版本 | 取决于上游；需要他们改构建环境 |
| B | 我们对 Linux 也自编（像现在 Windows 那样） | 要把上游源码和补丁纳入仓库，工作量不小 |
| C | 旧 glibc 系统上不支持 Agent Desktop 引擎，门禁白名单放行 | 零工作量；UOS 上这个引擎起不来，但默认的 CUA Driver 正常 |

**建议先选 C**，不阻塞主线。它只影响一个可选引擎；等上游或我们有空再做 A/B。

## 七、实施顺序

分四步，每步结束都有一个可验证的状态，出问题不会一把全赔进去。

1. **镜像**（第 1–4 项）。先只在本机 `docker build` 出 arm64 镜像，把三个编译在镜像里各跑一遍 —— 这次**全部用仓库自己的脚本**（包括之前只手抄过参数的 capture ffmpeg），确认 GLIBC 都是 2.28。这一步不碰任何现有 workflow。
2. **x64 补验证**。用 QEMU 出 x64 镜像，跑同样的三个编译。之前 x64 只验证了 sqlite，这一步把 ffmpeg 和 cua-driver 也验证掉。
3. **门禁**（第 6–7 项）。先加门禁但设成「只报告不失败」，接进 CI 跑一次，看它报出哪些文件 —— 预期正好是上表那几个，如果多出别的说明清单有遗漏。确认无误后再改成失败。
4. **切换编译步骤**（第 5、8–10 项）。三个 workflow 各改 3 步。先只改 `package-validation.yml`，用验证分支出一个包，在 UOS 上实测安装 + 启动 + SQLite 可用；通过后再改两个发布 workflow。

第 1、2 步无依赖，可以并行。第 4 步受验证预算约束（同一问题最多启动 4 次）。

## 八、证明成立的测试

- **镜像自检**：镜像 workflow 里构建后立即跑三个编译并检查 GLIBC，不合格不发布。
- **门禁单测**：构造带不同 GLIBC 版本符号的 ELF 夹具，验证「超过上限报错」「白名单命中放行」「白名单项必须带原因」。
- **产物实测**（最终验收）：验证分支出的 arm64 deb，在 UOS 真机上
  1. `dpkg -i` 成功（同时验收之前修的硬链接）；
  2. 启动后日志里**没有** `Database initialization failed`；
  3. 录屏（ffmpeg）和电脑操作（cua-driver）各走一次。
- 回归范围：`npm run test:scripts`（门禁单测在这里）；macOS / Windows 的打包不受影响，不需要重跑。

## 九、风险与回退

| 风险 | 缓解 | 回退 |
|---|---|---|
| buster 已 EOL，`archive.debian.org` 某天不可用 | 镜像是预构建的，日常 CI 只拉取不 apt；archive 是 Debian 的长期归档 | 镜像已推到 GHCR，不依赖 archive 可用 |
| QEMU 下编 git / cua-driver 很慢 | 只在重建镜像时发生，低频 | 镜像 workflow 超时设 2 小时 |
| 三个 workflow 各改一遍容易漏 | 用复合 action 收口，每处只改一行；门禁会拦住漏改的那个 | 按 workflow 逐个切换 |
| 缓存键变化导致一次冷编 | 有意为之，一次性 | 无需回退 |
| 容器里 root 运行导致产物属主错 | action 里以 runner uid/gid 运行 | — |
| gcc 8.3 将来编不了某个新依赖（如依赖开始用 `<compare>`） | 门禁会拦；届时装新版 gcc 到镜像里（still glibc 2.28） | 升级镜像内的 gcc，不影响方案 |
| 镜像 tag 与 workflow 不同步 | tag 从 `versions.env` 读；镜像内容哈希进 tag | — |

整体回退：把三个步骤改回 runner 上直接跑即可，门禁保留但会报错（提醒问题回来了）。镜像和 action 文件留着不影响任何东西。

## 十、不在本计划内

- `agent-desktop` 的上游沟通或自编（第五节，待定）。
- x64 的 UOS 1050 真机验收（没有机器）。
- Wayland 下的缩放、输入法、托盘等可用性问题。
- 捆绑的 Node 24.14.0（需要恰好 2.28，没有余量）—— 这是 Node 上游的事，本计划不涉及。

## 偏离记录

实施中偏离原计划的逐条补记（原因 + 同步的 commit）。

### 第 1 步：镜像与三个编译（2026-11-24，本机，arm64）

**三个编译全部通过，且全部用仓库自己的脚本、CI 同款调用**：

| # | 仓库入口 | 最高 GLIBC | 验证 |
|---|---|---|---|
| 1 | `npm run rebuild:better-sqlite3` | 2.28 | 加载成功，SQLite 3.54.1 |
| 2 | `node scripts/prepare-release-capture.mjs --arch arm64` | 2.28（koffi.node 2.25） | 仓库准入记录已写；H.264 / VP9 编解码通过 |
| 3 | `build-resource-artifacts.mjs measure helper -- bash scripts/computer-use/build-helper.sh` | 2.28 | `cua-driver 0.38.0` 启动；cargo 175 秒 |

这比方案里的验证更严格：方案阶段只有 cua-driver 是用仓库脚本编的，sqlite 和 ffmpeg 是用我自己的探针。
改用仓库脚本后立刻暴露了一个探针没撞到的问题（见下一条）。

**镜像清单比方案多了两项**：

1. **curl 要从 buster-backports 装 7.74**。buster 自带的 7.64 不支持 `--retry-all-errors`（7.71 起才有），
   而仓库的下载脚本有 3 处用了它 —— capture 步骤在下载 ffmpeg 源码时就失败了。
   探针没发现是因为探针里的 curl 调用是我自己写的，没有这个参数。
2. **rustup 的 `RUSTUP_HOME` / `CARGO_HOME` 必须在安装前就设成 `ENV`**。以行内环境变量的方式给
   `rustup-init` 的话，工具链会装到一处，而同一层后面的 `rustc --version` 去另一处找，报 "no default is configured"。

**一个对第 4 步有直接影响的发现**：capture 脚本会把产物的**绝对路径**写进 `package.json`
（`"from": "/work/resources/capture/linux-arm64"`）。容器里的路径在 runner 上不存在，打包会失败。
所以第 4 步的复合 action **必须把 workspace 挂载到与 runner 上完全相同的路径** ——
这不是优化，是让现有脚本不改一行就能工作的前提。方案 4.1 里原本把它列为第 1 条，现在有了具体证据。

### 第 3 步：门禁（2026-11-24）

门禁脚本 `scripts/client/linux-glibc-gate.mjs` 提前做了（方案里排在第 2 步之后），因为它不依赖镜像，而且越早接入越能防回归。

**自己解析 ELF，不用 `readelf`**：方案里没规定实现方式。选择自己解析是因为门禁的结论不应随 runner 装了什么而变
（实测中裸 `debian:10` 镜像就没有 `readelf`）。解析器与 `readelf -V` 在 5 个真实二进制上逐一对上。

**顺带修掉一个既有 bug**：`linux-package-policy.cjs` 里的 `checkGlibcFloor`（上一轮为 `make dev-uos` 加的）
把 glibc 版本当小数比较 —— `GLIBC_2.9` 被当成 2.9，大于 2.28，会被误拦；`GLIBC_2.10` 被当成 2.1。
已改为按「主、次两个整数」比较，并加了回归单测。

**白名单模式修正**：初版写成 `agent-desktop/*/…`，实际路径相对安装目录、带 `resources/` 前缀，
永远匹配不上 —— 单测抓到后改为 `resources/agent-desktop/*/agent-desktop-linux-*`。

**验证**：

- 12 个单测（测试运行时现场构造最小 ELF 作为夹具，不塞大二进制）。
- 真实产物：三个容器产物放行，两个 agent-desktop 按白名单豁免并打印原因。
- 反向：放入 CI 现编的 SQLite 模块（GLIBC_2.34），门禁失败并指出文件与版本。
- `npm run test:scripts`：487 项，482 通过 / 5 项既有条件跳过 / 0 失败。

### 顺序调整

方案里第 3 步是「门禁以只报告模式接进 CI」，第 4 步才是「切换编译步骤」。实际执行中把门禁脚本的编写与单测提前了，
但**接入 CI 仍按原顺序**：先只报告、确认它报出的文件清单与预期一致，再改成失败。

### 第 2 步：x64 与两个架构的端到端（2026-11-24，本机）

**镜像清单又多一项：nasm 要从源码编 2.16.03。** buster 自带的 2.14 汇编不了 FFmpeg 8 的 x86 代码
（`libavcodec/x86/vp8dsp.asm:416: error: (ALLOC_STACK:4) expecting ')'`），x64 的 capture 构建在 make 阶段失败。
arm64 没有 x86 汇编，所以同样的脚本在 arm64 上是通过的 —— 这个问题只有在 x64 上才暴露。
buster-backports 里没有更新的 nasm。换成 2.16.03（nasm.us 官方最新）后，失败的文件一次汇编通过。
Docker 的 `TARGETARCH` 是 `amd64`/`arm64`，而 Node 的包名是 `linux-x64`/`linux-arm64`，两者要分开映射，
否则 x64 下载 Node 时 404（arm64 时两者恰好同名，所以没暴露）。

**复合 action 在走真实路径时暴露了一个 bug。** 之前的验证用的是我自己写的测试脚本，以 root 运行；
换成走 action 的代码路径后，x64 的 cua-driver 立刻失败：

```
error: failed to create directory `/opt/cargo/registry/cache/...`
  Permission denied (os error 13)
```

镜像里 `CARGO_HOME=/opt/cargo` 属于 root，而 action 以 runner 的 uid/gid 运行，cargo 写不了 registry。
修法：容器内的 `CARGO_HOME` 指到挂载的 HOME 下。工具链本身在 `/opt/rustup`，只读即可。
这再次说明：**只有走 CI 将要走的那条路验证，才算验证过。**

**顺带清理了 action 里三处不实之处**（都是凭想象写的）：

- `/pnpm-store` 的挂载依赖一个 CI 里并不存在的环境变量 `PNPM_STORE_PATH`；
- cargo registry 的挂载指向 runner 的 `~/.cargo/registry`，与容器内实际的 `CARGO_HOME` 无关；
- 登录的 registry 听命于环境变量 `REGISTRY`，可能与镜像地址对不上。改为取自镜像地址的常量。

容器的 HOME 整体在 `RUNNER_TEMP` 下并已挂载，pnpm / cargo / node-gyp 的缓存都在其中，重跑自然复用，
所以那几个单独的挂载是多余的，已删除。一次 cargo 下载中断（`transfer too slow`，网络问题）后重跑，
243 个 crate 直接命中缓存，只补下了剩下的 171 个。

**`corepack enable` 在容器里静默无效。** 以非 root 运行时写不了 `/opt/node/bin`，命令退出码 0 但什么都没做。
不需要它：直接 `corepack pnpm`，它按当前目录 `package.json` 的 `packageManager` 字段选版本。
实测在仓库根目录得到 pnpm 10.27.0，在 `nuwa-electron-shell/` 得到 9.15.5 —— **工作目录决定版本**，
发布 workflow 是在后者运行的，与锁定版本一致。

**结果（两个架构都走复合 action 的代码路径，逐步使用与发布 workflow 相同的输入）：**

| 步骤 | x64 | arm64 |
|---|---|---|
| 安装依赖 | 通过 | 通过 |
| better-sqlite3 | 通过 | 通过 |
| capture ffmpeg | 通过（nasm 修复后） | 通过 |
| cua-driver | 通过（CARGO_HOME 修复后） | 通过 |

八个产物经 `readelf` 独立核对：架构各自正确，最高 GLIBC 全部 **2.28**（koffi.node 为 2.25），
最高 GLIBCXX 3.4.21（低于 UOS 的 3.4.25）。门禁对两个架构都通过。

**镜像 tag 改为纯内容哈希**（方案里是"日期 + 哈希"）：同样的内容永远是同一个 tag，重复构建幂等，
不会出现两个 tag 指向同一份内容。

**一条既有测试需要更新**：`release-workflows.test.mjs` 逐条确认安全关键的接线，其中两条断言把
`MSYS2_LOCATION` 和 `NUWAX_CAPTURE_MAC_SIGNING` 的 YAML 写法写死了（`KEY: value`）。这两个变量现在
经复合 action 的 `env:` 块传入（`KEY=value`），值本身一字未变。断言放宽为接受两种写法，
并新增了几条结构性断言：三个编译步骤必须走复合 action、不得用裸 `run` 绕过、capture 保留 30 分钟超时、
门禁步骤在位且排在产物校验之后。

### 按 QA 包验证的方案作废

曾计划给 `release-electron-dev.yml` 加 `workflow_dispatch`，在不发布的前提下出安装包做验证。
按用户决定不再走这条路：直接用 beta 构建验证。相关改动已撤回，workflow 的触发条件仍只有 tag 推送。

### 第 4 步：接入 CI（2026-11-24）

按依赖顺序分三个提交推送，保证任何时刻 CI 都不会去拉一个还不存在的镜像：
门禁脚本 → 镜像定义与复合 action（推上去后镜像 workflow 自动构建并推送）→ 发布 workflow 切换。

**推上去之后连续暴露了三个问题，都是本地验证不出来的。** 这是把"镜像定义"和"发布 workflow 切换"分开推的价值：
前两次失败时，还没有任何发布流程依赖这个镜像。

1. **镜像 workflow 首次运行即失败**：`base name (${DEBIAN_BASE_IMAGE}) should not be blank`。
   构建步骤引用 `steps.image.outputs.build-args`，而解析步骤只输出了 `tag`。
   同时 `build-args` 子命令的输出格式也不对 —— 它每行交替输出 `--build-arg` 和值（`docker build` 命令行的写法），
   而 `docker/build-push-action` 要的是每行一个 `KEY=value`。两个格式都保留：命令行用 `buildArgs()`，
   action 输入用这个子命令。修完后把那段 shell 在本地原样跑过（18 个变量 18 行）才推。

2. **门禁 CI 失败在我写的 readelf 对照测试上**。本机没有 `readelf`，这条测试一直提前返回，
   第一次真正执行是在 CI runner 上。解析器的结论是对的，错的是测试：`readelf -V` 打印三段
   （符号表、Version definition、Version needs），测试从整份输出里取最大值，
   拿 `libc.so.6` **自己导出**的版本去和门禁比较 —— 而"导出"和"需要"是两回事，加载器只检查后者。
   （CI 上报的 `GLIBC_2.43` 是它的排序把 `2.4` 当成最大、再拼出来的假值。）
   改为按段落标题切块、只取 needs 段。修完后在带 `readelf` 的 Linux 容器里实跑才推。

3. **镜像验证 job 在两个架构的 runner 上都失败**：
   `EACCES: permission denied, mkdir '.../_temp/linux-native-home/.cache/node/corepack/v1'`。
   action 直接挂载容器的 HOME 而没有先创建它；宿主路径不存在时由 docker 创建，而 docker 以 root 运行，
   挂载点就属于 root，容器里以 runner 身份运行的用户写不了。
   **在 macOS 上复现不出来**：Docker Desktop / OrbStack 会把挂载点的属主映射成宿主用户；
   之前的本地验证里这个目录又恰好是预先建好的。
   在原生 Linux（Ubuntu 24.04 测试机，与 runner 同条件）上做了对照实验：
   不预先创建 → 挂载点属主 root、容器内写 `.cache` 报 Permission denied；预先以当前用户创建 → 写入成功。

**修完 HOME 属主后，在原生 Linux 上把复合 action 的完整路径重跑了一遍**（Ubuntu 24.04 测试机，
原生 x64、普通用户、与 runner 同条件，从零开始、不预先创建任何目录）：
安装依赖、better-sqlite3、capture ffmpeg、cua-driver 四步全部通过，cua-driver 产物最高 GLIBC_2.28。
这台测试机连不上 GitHub，cua-driver 的克隆经用户 Mac 上的代理完成（`192.168.31.7:8234`）——
与被验证的代码无关；GitHub runner 到 GitHub 是通的。

**教训**：本地"通过"不等于 CI 通过。三种本地盲区各出现过一次 —— 本机没有某个工具（`readelf`）、
测试条件比 CI 宽松（目录预先存在）、平台行为不同（macOS 的 docker 属主映射）。
能补的都在原生 Linux 上补做了。

### 第 5 步：用真实发布验证（2026-11-25，v3.3.0-beta.3 → beta.5）

按上面的调整，不做不发布的验证包，直接发 beta 来验证发布路径本身。一共发了三次。
前两次暴露的问题都在只有 tag 触发的发布流程才走得到的地方 —— 此前没有任何 workflow 走到过。

**v3.3.0-beta.3（未发布，tag 与草稿按规矩保留）**

1. **本机的发布被全局锁挡住**（`operation is already running`）：`make harness-local` 与发布共用
   `operation.lock`，预检不取锁，所以预检能过、正式运行才失败。没有任何东西被推送；停掉开发客户端后重跑。
2. **Linux 与 macOS 的构建拉不到镜像**（`unauthorized`）。镜像是私有的，拉取需要三件事同时成立：
   复合 action 声明 `GITHUB_TOKEN`（它默认不是环境变量，登录步骤读到空值后静默跳过）、
   发布 workflow 有 `packages: read`、`docker login` 收到的是 `ghcr.io` 而不是完整镜像路径（第三处是补测试时发现的）。
   **镜像 workflow 的验证 job 当时先做了一次预登录，把前两处全部盖住了** —— 改为验证 job 的第一次拉取也走复合 action，
   并且登录失败、拉取被拒都直接报错说明原因。
3. **macOS 的 capture 步骤 80 毫秒就退出**：GitHub 的 macOS 26 runner 没有 `timeout` 命令（本机有，所以本地看不出来）。
   步骤超时改由 Node 实现（先 TERM、宽限期后 KILL、超时退出码 124）。复合 action 有两个分支，
   镜像 workflow 的验证 job 只跑 Linux 那一支，所以加了 `native-platforms` job 在真实的 macOS / Windows runner 上跑另一支。
4. **Windows 在最后的门禁步骤失败**：门禁写死了 `--platform linux`，又没有限制只在 Linux 上执行。
   加了 `if: runner.os == 'Linux'`；门禁本身也改为拒绝与当前系统不一致的 `--platform`，而不是报"目录不存在"。

**v3.3.0-beta.4（未发布，tag 与草稿按规矩保留）**

Linux 两个架构的构建失败，原因是**原生件缓存命中了切换之前的产物**：缓存键里的 `nativeTools()` 探测的是 runner 上的编译器，
而编译已经搬进镜像，键没有因此变化。于是恢复了 Ubuntu 24.04 上编的 ffmpeg（需要 GLIBC_2.38），
紧接着被产物准入检查拦下（`拒绝覆盖未知或已改动的资源目录`）—— 第二道防线起了作用，没有流进安装包。

缓存恢复发生在复合 action **之前**，所以键必须在 runner 上就算得出来，不能去探测镜像内部。
做法是把镜像三个配方文件的内容哈希加进键（`linuxNativeBuildIdentity`，只在 Linux 上参与）：
镜像一变，缓存失效一次；每份缓存都与产出它的镜像绑定。门禁同时由只报告改为强制。

随后的门禁 CI 红了一次：缓存测试的夹具里没有 `docker/linux-native/*`，而新函数要求这三个文件存在。夹具补上后在 Linux 容器里跑过才推。

  发布 CLI 自动派发的补同步（run 45545293895）成功，S3 与 OSS 的 beta 指针均已指向 beta.5。
